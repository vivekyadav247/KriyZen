- Exact archive verification (2026-11-26): the four candidate tarballs matched the SHA-512 `dist.integrity` strings in registry metadata retrieved during research. A fresh registry read was proxy-blocked, but the saved archives were installed in the isolated runtime spike using a preserved lockfile. Candidate manifests are Apache-2.0, publish no `engines.node` field, and align declared plugin peer ranges.
- Exact core `dist/db.d.ts` defines `CorsairDatabaseInput = Pool | ...` importing `Pool` from `pg`. Its runtime adapter checks that the object has `query()` and `connect()` and constructs `new Kysely({ dialect: new PostgresDialect({ pool }) })`; runtime spike queries confirmed the shared `pg.Pool` worked with Corsair and Drizzle. Pool lifecycle behavior in KriyZen itself remains to be implemented and verified in P03.2.
- Core's `CORSAIR_CORE_TABLE_NAMES` is exactly `corsair_integrations`, `corsair_accounts`, `corsair_entities`, `corsair_events`, and `corsair_permissions`, with declarations for all five. Exact `setupCorsair` introspects tables and warns for missing ones, then creates integration/account rows and DEKs. It does not create table DDL. Its `createTestDatabase()` helper creates only the first four tables in in-memory SQLite and omits permissions; it is not a production initializer. Inspected package exports/files contain no migration CLI/runner or vendor migration history. The official five-table PostgreSQL DDL was applied and tested only in the disposable spike database; all catalog/schema and setup checks passed. Recommend independently versioned vendor SQL/history outside KriyZen's Drizzle config/history.
- Exact Gmail `0.1.13` factory defaults to OAuth 2.0 and embeds only `https://www.googleapis.com/auth/gmail.modify`. Calendar `0.1.10` embeds `https://www.googleapis.com/auth/calendar.events` and `https://www.googleapis.com/auth/calendar.freebusy`; this differs from the broader scopes listed in current plugin setup docs. Reconcile requested operations and least privilege before consent setup.
- Core `0.2.33` exports `generateOAuthUrl` and `processOAuthCallback` from `./oauth`. Self-managed flow requires tenant ID + redirect URI, returns HMAC-signed state, and callback requires the matching redirect URI; the optional `hubConnect` option changes the flow. `processOAuthCallback` documents code exchange and encrypted token persistence. Hub is not mandatory for this SDK OAuth path, though Hub remains a hosted alternative with separate terms/cost. No real OAuth was run.
- Isolated runtime spike (Node `24.13.0`, TS `5.9.3`, Zod `4.6.7`): imports and multi-tenant registration succeeded for both plugins; `listOperations` returned 24 Gmail and 6 Calendar operations; CLI `--help` / `--version` loaded; TypeScript compilation passed. Fetch/socket instrumentation saw zero network calls during core/plugin imports and registration. `npm audit` reported 0 advisories across 112 resolved dependency entries. Install scripts were disabled; core's inspected postinstall fetches checksum-verified `frpc` into the user cache, an optional tunnel dependency not needed for this spike.
- Runtime OAuth scope was limited: payload helper round-trip and account target passed, and malformed state was rejected as `invalid_state`. Static implementation applies HMAC-SHA256 using `kek`, enforces a 10-minute age, and callback uses the same `redirectUri`; package state contains plugin, tenant, timestamp and optional account target. No nonce/replay persistence or application-session binding was found. No Google credentials or provider requests used.
- PostgreSQL runtime passed after Docker was available. The official five-table DDL was applied only to the disposable database. pg, Drizzle, Corsair Kysely and plugin cache ORM operations succeeded on the same Pool; setup repeated without increasing integration/account counts; permission lookup/status lifecycle passed. Normalized KriyZen definitions and history matched before/after vendor setup. The disposable database was dropped and verified absent; the original database matched its full baseline afterward.
- DDL comparison found five tables and 39 columns consistent with core 0.2.33 types. The permission token has no unique constraint, `tenant_id` has no FK, and status is text without a DB CHECK; SDK code generates tokens and validates lifecycle values. Timestamp/JSONB definitions and account foreign keys matched. Recommend versioned vendor SQL with independent history; no SDK-owned migrator/history exists.
